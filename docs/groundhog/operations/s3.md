## Supported deployment

The first S3 release supports AWS general-purpose S3 buckets and S3 Standard storage. The process
uses the standard AWS credential provider chain and the configured AWS region. Keep credentials
outside `groundhog.toml`.

The release does not support custom endpoints, directory buckets, multipart upload, automatic
sealing, object deletion, remote orphan inventory, or migration between storage formats.

Groundhog stores authoritative state only in the configured bucket and prefix. Local configuration
and scratch files are replaceable. Scratch files must not be included in backups.

## First-release limits

The first-release checkpoint envelope has these maximum values:

- 100,000 receipts (lifetime batch commitments)
- 100,000 stream frontiers
- 1,024 active data references
- 1 GiB for one stored checkpoint object

The implementation also limits one stored segment object to 1 GiB.

Groundhog 0.3.0 qualifies S3 support at these limits. The same-region benchmark and live AWS gates
passed. The project owner approved the schema version 1 freeze and release qualification.

## IAM roles

Use separate initialization, serving, verification, and cleanup identities. Replace the example
bucket and prefix before use.

### Initialization role

Initialization lists only the configured prefix. It creates the format, checkpoint, commit, and
HEAD objects. It can also authenticate and reattach to an existing deployment.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-groundhog",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["groundhog/production", "groundhog/production/*"]
        }
      }
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::company-groundhog/groundhog/production/*"
    }
  ]
}
```

### Serving and sealing role

Serving and sealing use exact-key reads and conditional writes. They do not list or delete objects.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::company-groundhog/groundhog/production/*"
    }
  ]
}
```

### Verification role

Verification is read-only. It does not list objects, including during `--chain` verification.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-groundhog/groundhog/production/*"
    }
  ]
}
```

Do not grant `s3:DeleteObject` to initialization, serving, sealing, or verification identities.

## Initialization and reattachment

Run:

```sh
groundhog init /srv/ground/acme \
  --backend s3 \
  --bucket company-groundhog \
  --region us-west-2 \
  --prefix groundhog/production
```

If all local files are lost, run the same command with the same bucket, region, and prefix.
Groundhog authenticates the remote deployment before it writes replacement local configuration.
It accepts complete advanced histories and recognized partial initialization states. It rejects
unrelated or malformed objects.

## Normal commands

Start the server only after initialization or successful reattachment:

```sh
groundhog serve --config /srv/ground/acme/groundhog.toml
```

The command claims remote writer authority before it binds the Unix socket. Graceful shutdown closes
mutation admission, completes admitted mutations, and then releases writer authority.

Run active-object verification with:

```sh
groundhog verify --config /srv/ground/acme/groundhog.toml
```

Run complete parent-chain verification with:

```sh
groundhog verify --chain --config /srv/ground/acme/groundhog.toml
```

A conclusive verification failure exits with status 3. A provider, credential, network, or scratch
failure exits with status 1. Invalid configuration exits with status 2. Unsupported configuration
exits with status 4.

## Planned seal outage

Run this procedure before the deployment reaches 1,024 active chunks or 256 MiB of stored active
chunk bytes, whichever occurs first. The first release does not expose these values as service
metrics. Track acknowledged batch count and stored data volume in the operator system. Schedule the
outage with sufficient margin for unmeasured traffic.

1. Stop new client writes.
2. Stop `groundhog serve` gracefully.
3. Wait for the process to exit. Do not start `seal` while `serve` is running.
4. Run active verification.

   ```sh
   groundhog verify --config /srv/ground/acme/groundhog.toml
   ```

5. Run the manual seal.

   ```sh
   groundhog seal --config /srv/ground/acme/groundhog.toml
   ```

6. Run active and full-chain verification.

   ```sh
   groundhog verify --config /srv/ground/acme/groundhog.toml
   groundhog verify --chain --config /srv/ground/acme/groundhog.toml
   ```

7. Start `groundhog serve`.
8. Confirm one finite replay and one exact retry of the last acknowledged batch.
9. Resume client writes.

`seal` first reads HEAD and refuses a non-null writer session. It does not take over or fence a live
server. Each successful segment publication is durable independently. If a later group fails, a
retry processes only the remaining active chunks. Groundhog keeps all removed chunk objects.

If the server did not stop cleanly, restart `serve` first. Normal writer recovery resolves or takes
over the previous session. Stop it gracefully before you retry `seal`. Do not add or use a force-seal
procedure.

If `seal` reports an unknown HEAD result, restart `serve` to perform normal recovery. Do not edit
HEAD and do not delete immutable objects. After the server opens successfully, stop it gracefully,
verify, and retry the seal procedure.

## Fencing, poisoning, and recovery

HTTP 503 means that this process cannot safely accept the mutation. Retry the same source, batch ID,
and content only after a healthy writer is available.

- A fenced writer has lost the active writer session. Stop it and use the writer that owns HEAD.
- A poisoned writer found an outcome or history it could not authenticate. Its last confirmed
  snapshot remains readable. Stop writes, preserve the exact prefix, and run verification.
- An ambiguous client response does not prove that the batch failed. Retry the identical batch.
  Groundhog returns the original receipt when it committed.
- Do not repair `HEAD.json`, commits, checkpoints, indexes, chunks, or segments manually.

For a provider or credential outage, restore exact-key `GetObject` and `PutObject` access and restart
the server. For confirmed corruption, stop all writers and preserve the prefix for investigation.

## Test cleanup role

Production Groundhog code never deletes remote objects. A separate external cleanup role can delete
only one unique `groundhog-tests/<run-id>` child prefix.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-groundhog",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["groundhog-tests/2026-08-11-001", "groundhog-tests/2026-08-11-001/*"]
        }
      }
    },
    {
      "Effect": "Allow",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::company-groundhog/groundhog-tests/2026-08-11-001/*"
    }
  ]
}
```

Confirm the bucket, region, and exact child prefix before cleanup. Never set the cleanup target to a
bucket root or production prefix. With the restricted cleanup credentials, run:

```sh
aws s3 rm \
  s3://company-groundhog/groundhog-tests/2026-08-11-001/ \
  --recursive \
  --region us-west-2
```

## Live qualification

The live AWS gates passed for Groundhog 0.3.0. The results cover the provider contract,
response-loss reconciliation, local-state loss, restricted IAM, and same-region performance.
Release validation records the evidence hashes and refuses S3 version-1 qualification while a
required gate is not passed.

Use one new no-delete root child prefix for each resumed run. The tests create these children under
`$GROUNDHOG_TEST_S3_PREFIX`:

- `provider`
- `seal`
- `runtime-conformance`
- `lost-response`
- `binary-local-loss`
- `checkpoint-envelope`
- `offered-load`
- `restricted`
- `restricted-serving`

Activate the initialization identity. Then export the test configuration:

```sh
export GROUNDHOG_TEST_S3_BUCKET=company-groundhog
export GROUNDHOG_TEST_S3_REGION=us-west-2
export GROUNDHOG_TEST_S3_HOST_REGION=us-west-2
export GROUNDHOG_TEST_S3_PREFIX=groundhog-tests/2026-08-11-001
export GROUNDHOG_TEST_S3_NETWORK_CONDITIONS='same-region release host; no traffic shaping'
```

Run the general integration tests with the initialization identity. Exclude the restricted-role
test because it requires different credentials:

```sh
cargo test --locked -p groundhog-s3 --test s3_integration \
  -- --ignored --nocapture \
  --skip restricted_role_recovers_ambiguous_no_effect_create_without_list
cargo test --locked -p groundhog-cli --all-features --test s3_release -- --ignored --nocapture
cargo test --locked --release -p groundhog-cli --features test-support --test s3_benchmarks \
  checkpoint_release_envelope -- --ignored --nocapture
cargo test --locked -p groundhog-s3 --test s3_benchmarks \
  same_region_offered_load -- --ignored --nocapture
```

Keep the initialization identity active. Initialize both restricted children with separate local
roots:

```sh
RESTRICTED_RECOVERY_LOCAL_ROOT="$(mktemp -d)"
groundhog init "$RESTRICTED_RECOVERY_LOCAL_ROOT" \
  --backend s3 \
  --bucket "$GROUNDHOG_TEST_S3_BUCKET" \
  --region "$GROUNDHOG_TEST_S3_REGION" \
  --prefix "$GROUNDHOG_TEST_S3_PREFIX/restricted"

RESTRICTED_SERVING_LOCAL_ROOT="$(mktemp -d)"
groundhog init "$RESTRICTED_SERVING_LOCAL_ROOT" \
  --backend s3 \
  --bucket "$GROUNDHOG_TEST_S3_BUCKET" \
  --region "$GROUNDHOG_TEST_S3_REGION" \
  --prefix "$GROUNDHOG_TEST_S3_PREFIX/restricted-serving"
```

Remove the initialization credentials from the AWS credential provider chain. Activate the serving
identity. Give it `GetObject` and `PutObject` for only these two object prefixes:

```text
$GROUNDHOG_TEST_S3_PREFIX/restricted/*
$GROUNDHOG_TEST_S3_PREFIX/restricted-serving/*
```

Do not give this identity `ListBucket` or `DeleteObject`. Run the two restricted tests separately:

```sh
cargo test --locked -p groundhog-s3 --test s3_integration \
  restricted_role_recovers_ambiguous_no_effect_create_without_list -- \
  --ignored --exact --nocapture
cargo test --locked -p groundhog-s3 --test s3_restricted \
  restricted_serving_role_uses_no_list_or_delete_permission -- \
  --ignored --exact --nocapture
```

These tests open existing deployments without listing or deleting objects. The second test also
claims, appends, replays, drains, and releases. A passing run under broader credentials is not
restricted-IAM evidence.

Keep the cleanup identity inactive until all tests and evidence recording finish. Then remove the
serving credentials and activate the cleanup identity. Delete only the complete
`$GROUNDHOG_TEST_S3_PREFIX` root child. Do not reuse that root child for a later run.

The checkpoint gate uses the CLI native scratch path and the production S3 provider. It runs ten
build-and-upload samples on a same-region release host. It records build, upload, and total p50,
p95, and maximum times. It records canonical and stored bytes with the applicable size limits.
It also records CPU, peak RSS, host memory, bucket region, host region, and network conditions. Total
p95 must not exceed 30 seconds. Peak RSS must not exceed 1 GiB.

The offered-load gate records request count, concurrency, elapsed time, throughput, p50, p95, p99,
and error count. Record both outputs in a reviewed evidence update before changing a live gate to
`passed`.

The schema version 1 vectors are complete and frozen for Groundhog 0.3.0. Every live gate passed
before the project owner approved the freeze and release qualification.
